# Явное продолжение неизвестного запроса итогов

Scope: локальный Secretary; восстановление только `summarize`, без повторной STT.
Случай: ответ Polza потерян, старое задание `uncertain`, часть шагов сохранена.

## Контракт

- Актор — владелец локального приложения через существующие Origin/CSRF проверки.
- Новый POST `/api/v1/meetings/{meeting_id}/summary-resume` принимает
  `source_job_id`, `transcript_version`, `operation_id` (UUID) и обязательный
  `acknowledge_possible_duplicate_charge: true`. Без явного подтверждения POST
  не допускается; обычный запуск и автоповтор по-прежнему не обходят `uncertain`.
- Источник обязан принадлежать этой встрече и текущей версии, иметь stage
  `summarize`, status `uncertain` и валидный сохранённый frozen summary context.
  Текущие исходники, roster/attribution и пин модели должны соответствовать этому
  контексту. Смена версии/контекста, активная обработка или другой новый intent —
  конфликт; никаких новых платных запросов при конфликте.
- Идемпотентность и единственный дочерний job для source обеспечиваются атомарно
  SQLite. Повтор той же команды возвращает тот же job. Другая команда для уже
  продолженного source не создаёт ещё один job. UUID не является обещанием
  идемпотентности со стороны Polza.
- Хранение: добавочная migration 10 с immutable `summary_resume_operations`,
  UNIQUE source/child и deferred FK. У summary `uncertain` исключается из старого
  active unique index только вместе с DB guards INSERT/UPDATE: unresolved uncertain
  leaf запрещает обычное новое задание, разрешён лишь его атомарно связанный child.
  Индекс и ограничения STT не ослабляются. Source job не получает ложный terminal state.
- Новый job ссылается на `resumed_from_job_id`, наследует frozen context и использует
  существующие exact-key checkpoints после обычной проверки evidence. Незавершённый
  шаг может быть оплачен повторно, затем обработка оставшейся части продолжается.
- Старый job остаётся `uncertain`; неизвестные расходы/резервы остаются в обоих
  ledger. Нельзя объявлять запрос бесплатным, отменённым или завершённым, подменять
  provider ID кандидатом из истории или освобождать неизвестный расход.
- Только для вычисления текущего processing state исходный job с доказанной
  локальной дочерней связью уступает место дочернему. Это не финансовое разрешение
  неопределённости. Новая неопределённость дочернего job требует нового явного решения.
- Успешный ответ возвращает `job_id` и `source_job_id`. Cloud/бюджетные admission,
  выключенный runtime и существующие guards действуют для нового job как обычно.

## Интерфейс и проверка

В карточке неизвестных итогов: расшифровка сохранена, ответ/расход последнего запроса
неизвестны. Кнопка «Продолжить итоги» открывает короткое подтверждение риска оплаты.
Подтверждение создаёт ровно одну команду; двойной клик и повтор ответа не дублируют её.
Ключ, модель и технические настройки пользователь заново не вводит.

Приёмка: strict acknowledgement, чужой/stale/non-summary source, context mismatch,
double-submit/concurrency, исходный ledger неизменён, checkpoint reuse без повторной
STT, обычный uncertain guard сохранён, отображение дочернего прогресса/результата.
Offline tests используют mock transport; live replay выполняет только владелец
после понятного предупреждения либо агент по отдельному точному разрешению.

Rollback: убрать новый UI/route, сохранив jobs/lineage и billing evidence. Не очищать
старые задания/расходы для имитации успешного восстановления.
Перед активацией migration сохранить холодную копию рабочих SQLite в Secretary.
Не понижать схему рабочей БД старым приложением; копия предназначена для отдельного
контролируемого восстановления, а не для автоматического затирания новых данных.
