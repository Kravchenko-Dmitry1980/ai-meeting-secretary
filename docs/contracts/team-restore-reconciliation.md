## Реализованный контракт R0/R1

R0 защищает обычный `api.create_app`, включая `run_worker=false` и `outbound_enabled=false`. Проверяется effective Secretary/Billing path до каталогов, `tempfile.tempdir` и dependency factories. Database читает исходный guard при каждом соединении; диагностическое открытие guarded authority использует SQLite `mode=ro`, не выполняет migrations/recovery и запрещает DML/DDL/ATTACH/mutating PRAGMA. Для inactive main без sidecars чтение не создаёт WAL/SHM. Существующие journaled stores читаются обычным read-only SQLite, без игнорирования журнала. Это не доказательство остановки чужого writer.

R1 — явная локальная команда `reconciliation-preview` с двумя абсолютными путями: завершённый архив и отдельный каталог восстановления. Нет `--apply`, owner defaults, чтения environment, сетевых вызовов или запуска процессов.

Входы: полный manifest и его SHA-256, точный `restore.json`, три одинаковых immutable guards, четыре отдельные базы Secretary/Team/Billing/Vikunja, перенесённые asset roots и файлы из manifest. Поддерживаются текущие Secretary/Team schema 9 с точным migration set `{1..9}`, Billing с set `{3}`; native storage `local-v2.7.0`. База, остановленная на schema 7/8, или иная схема требует новой проверенной карточки; preview её не мигрирует.

Выход: `state=preview_blocked`, `activation_supported=false`, `outbound_enabled=false`; restore/manifest/metadata/bindings digests, schema/logical/file hashes, counts известных work/auth families, хеши перенесённых файлов, неисполненные условия активации. Содержимое сообщений, полные transcripts, ключи, credentials, raw provider bodies и строки SQLite не выводятся. Неизвестное значение состояния выводится как `other`.

Billing отдельно показывает `reserved/submitted/uncertain`: число строк, сумму исходных `reserved_micro` и `gross_hold_micro = sum(max(reserved_micro, observed_cost_micro))`. Это валовые удержания по операциям, **не** доступный остаток общего месячного бюджета и не подтверждённый провайдером расход. Provider/account overlap и действующий лимит 3000 ₽ остаются предметом существующей Billing authority и отдельной текущей сверки. Preview не освобождает резерв и не изменяет ledger.

Архивные и восстановленные базы при preview должны не иметь WAL/SHM/journal. Любой sidecar означает отказ; его нельзя автоматически удалять или игнорировать ради PASS. Проверка архива и архивные asset inspections в BackupService используют inactive immutable RO. Исторический архив со служебными файлами старой версии остаётся сохранённым и требует отдельного разбора либо новой корректной копии; текущая команда его не ремонтирует.

Все объявленные archive members и восстановленные assets проверяются и повторно сравниваются вместе с metadata/четырьмя DB в конце. Capture manifest сравнивается с исходным документом после только известного преобразования путей. Digest связывает конкретные расположения файлов и metadata. Он описывает прочитанные данные, **не** заменяет maintenance barrier, fresh owner approval, provider evidence или будущую повторную проверку перед активацией.

Пределы SQL inventory: 100000 строк суммарно, 512 таблиц на источник, 1 MiB SQLite row до extraction, 64 MiB суммарного сериализованного содержимого, 30 секунд SQL inventory. Hashing архива/аудио/файлов и финальная сверка входят в отдельную файловую работу; полный preview не имеет квалифицированного SLA 30 секунд. Это не измерение пикового RAM всего процесса.

### R4 shared permission predicate: контракт и текущая карта sinks

**Статус: CONTRACT DESIGN ONLY; runtime predicate и activation permit не реализованы.** Пока хоть один источник, owner/provider proof, native proof или execution lineage отсутствует, противоречив либо изменился после проверки, результат только `activation_blocked`/unavailable; оба флага `activation_supported` и `outbound_enabled` остаются `false`. Неизвестное состояние трактуется как отказ. Будущий `permit` возможен только после отдельного контролируемого перехода всех четырёх source guards в одну и ту же committed activation generation; evaluator сам не может переопределить restore markers или SQLite read-only authorizer.

Кандидат на authority — один внутренний evaluator, связанный с точным `TeamRuntimeSettings` от штатного loader и `ResolvedRuntimeRestoreContext`. Он обязан сам получить current R3 decision/readbacks и bindings для одного `restore_id`: все четыре authorities, file identities/content commitments, manifest/metadata/inventory/scope, current provider observations, current owner decision, native authenticated GET с advancing head и fresh execution/auth lineage. Нельзя принимать caller booleans, caller-selected source paths, detached receipts или настройки как разрешение. Результат должен быть typed и sanitized: blocked/unknown либо ограниченный permit, связанный с restore epoch, proof digest, action, participant и durable operation id; permit не сериализуется в config и не переиспользуется между операциями.

Для будущего permit точка потребления должна повторно сверять его в том же interlock, который удерживает side effect: SQL mutation — внутри защищённой transaction/admission; recovery/claim/reservation — до изменения durable state; paid/provider dispatch — после reserve и непосредственно перед POST; native operation — непосредственно перед exact process/API boundary. После возможной отправки наружу сохраняются действующие правила `uncertain`/no-replay`. Между разными SQLite-файлами нет общей атомарной транзакции: любой частичный prepare, readback или crash оставляет все runtime sinks blocked; одного набора четырёх похожих флагов недостаточно. Все четыре guards должны оставаться действующими veto до единого committed transition; частично снятый guard не может дать доступ через локальный standalone app. `MaintenanceRepository` — кандидат на общий drain/barrier: `begin_barrier()` переводит gate в `draining` и повышает fence, новые tickets блокируются, а `freeze()` требует завершения active tickets. Но текущие tickets не содержат R4 proof/source-generation digest, и не каждый standalone entry path принудительно использует owner-side repository. Поэтому текущий barrier годится только как lifecycle interlock, не как activation permission. Перед кодовым подключением надо решить ticket binding/schema migration и доказать coverage/lock ordering для всех sinks.

| Sink | Текущая защита в checkout | Что ещё требуется от общего predicate |
|---|---|---|
| Secretary startup | `api.create_app()` проверяет Secretary/Billing markers; `create_secretary_team_app()` и `TeamRuntime.start()` проверяют весь набор источников до обычной работы | Проверить актуальное owner/provider decision, native head и lineage; связать решение с exact config/source generation |
| SQL | `Database.connection()`, `TeamDatabase.connection()` и `BudgetRepository.connection()` проверяют свой source marker при каждом подключении; guarded DB открывается read-only; maintenance admission — отдельный lifecycle fence | Общая source generation + operation-bound decision должна удерживаться внутри той же транзакции, включая путь без marker-строки |
| Recovery, claims, reservations | Startup recovery/Team recovery и repository claims используют local restore checks, maintenance admission и/или source fences | Все mutation/claim/reserve входы должны получить один и тот же authoritative decision и fail closed на stale proof |
| Paid dispatch | Polza gate проверяет настроенные authority paths в preflight и непосредственно перед billing submit | Тот же epoch-bound decision и operation lease должны пройти reserve → final submit без второго независимого allow-path |
| Task/notification dispatch | `TeamRuntime._loop()` оборачивает каждый штатный scheduled worker в `admitted_operation()` и удерживает ticket до completion/receipt; `PublicationWorker` дополнительно использует собственный `async_admission`; workers сохраняют claims, repository checks и request/operation fences | Общий predicate должен быть связан с этой admission-lease и финальным transaction/dispatch seam; прямое использование worker вне owner runtime остаётся без lifecycle admission; неизвестное внешнее завершение — `uncertain`, без replay |
| Native | Managed native lane даёт diagnostic source custody; в текущих evidence нет квалифицированного authenticated GET/advancing head или activation caller | Exact native proof должен входить в тот же decision; не расширять process allowlist и не запускать RW fallback |

Текущая evidence gap подтверждена source search: `current_activation_consent_commitment()` и `record_blocked_activation_decision()` существуют без runtime caller; ledger разрешает только `activation_blocked`. `restore_runtime_context.resolve_runtime_restore_context()` — read-only resolver и также не является authority/caller. Применимые проверки и ограничения записаны в [R4 runtime guard validation](../TEAM_R4_RUNTIME_GUARD_VALIDATION.md).

**Acceptance для реализации:** (1) synthetic RED на каждый sink без predicate и GREEN после подключения; (2) отсутствующий, просроченный, чужой или изменившийся proof блокирует до SQL/provider/native side effect; (3) interleaving между initial check и commit/POST не обходит lease/fence; (4) crash после частичных четырёх-source preparations оставляет всё blocked и не replay-ит исторические операции; (5) все тесты используют disposable synthetic authorities, а live owner/provider/native acceptance остаётся отдельным gate. Пока native proof и fresh lineage не подтверждены, успешный test fixture не может создать `activation_granted`.

### Предложение: operation-bound admission ticket v1

**Статус: offline DTO contract implemented; durable repository binding and runtime permission remain absent.** Existing `MaintenanceTicket` остаётся lifetime/drain receipt. Для restored generation его нельзя считать разрешением. `R4AdmissionBindingV1` содержит только непрозрачные IDs/digests: `deployment_id`, `restore_id`, `r3_id`, `epoch_id`, `source_generation_sha256`, `decision_id`, `decision_sha256`, `action`, `participant_id`, `run_id`, `operation_id` и текущий `barrier_fence`. Канонический `source_generation_sha256` связывает фиксированный R3 inventory и manifest/metadata, все четыре role/file identities и R3/R4 preparations/readbacks, config versions, native schema и authenticated watermark. Суммировать mutable business DB целиком нельзя: обычная разрешённая работа меняет строки.

Binding создаёт только внутренний evaluator на путях из штатно загруженной конфигурации и fixed R3 inventory. Caller booleans, произвольный source path, detached receipt и простой факт наличия нового control DB не могут его создать. `decision_sha256` должен указывать на единственное актуальное committed решение, покрывающее current owner/provider evidence, native advancing head и fresh execution/auth lineage. `activation_blocked`, missing/stale/unknown evidence, несовпадение source identity, неправильное действие/участник/run/operation или replay означают отказ до первой мутации/отправки. Binding не содержит token, личный payload или raw proof.

`MaintenanceTicketV1` реализован как чистый versioned DTO в `restore_admission_binding.py`: он связывает `ticket_id`, deployment, participant, run, kind, operation, fence и `R4AdmissionBindingV1`. Для известных `outbound_bot`, `outbound_notification`, `outbound_subscription`, `outbound_task` и `outbound_polza` kinds соответствие action фиксировано. Строгий record round-trip сверяет точный набор полей, checksum и поколение `SourceGenerationV1` либо `SourceGenerationV2`; missing/v0 binding, stale generation и несовпадение scope отвергаются. DTO не читает источники и не делает запись в maintenance DB, поэтому пока не является durable ticket и ничего не авторизует. Старые tickets без binding остаются lifecycle-only и не могут авторизовать ни один restored sink. При будущей runtime реализации ticket должен удерживаться через полный owned lifetime: SQL commit; recovery/claim/reservation; provider request до receipt либо durable `uncertain`; native operation до завершения и readback. Если `begin_barrier()` выигрывает гонку первым, новые tickets не создаются. Если ticket уже начат, barrier повышает fence и ждёт именно его завершения; ticket может завершить только ту же операцию и сохранить receipt/uncertain без replay.

Maintenance DB и stopped-runtime evidence сейчас принимают фиксированный точный registry колонок, включая lifecycle-only `maintenance_tickets`; добавление binding-колонок или таблицы без versioned schema migration сломало бы restore validation. Новый DTO намеренно не подключён к consumers: diagnostic fixed-ledger reader существует только для текущего blocked состояния и не строит доверенное source generation; независимый source-generation reader, общий predicate/interlock и runtime admission всё ещё отсутствуют. Любая передача DTO от caller сама по себе не доказывает актуальность decision и не должна становиться allow-path.

Ни один локальный sink не доверяет одному ticket отдельно: startup, Secretary/Team/Billing SQL connections, recovery, claims/reservations, final Polza/MAX/Vikunja dispatch и native seam должны сверять одно и то же `decision_sha256` и generation. Все четыре source guards и immutable history остаются на месте. Будущий R4 evaluator сможет классифицировать marker как исторический только при наличии одного финального committed decision, четырёх совпадающих source grants/readbacks и текущего operation-bound ticket; любое partial state оставляет existing read-only authorizers и active guards fail-closed. `DELETE`, `UPDATE ... reconciliation_required=0`, снятие trigger или per-file разрешение запрещены.

Из-за отсутствия общей транзакции для четырёх SQLite переход должен быть двухфазным по смыслу: подготовить и durable-readback все четыре immutable grants, затем записать final decision в fixed R3/activation ledger последним. Каждый sink обязан прочитать final decision и совпадающие grants всех четырёх источников; отсутствие ledger, неполный набор или crash до последнего commit остаются blocked. Старый R3 reader не расширяется до writer. До появления такого verifier `MaintenanceRepository` остаётся только drain/barrier и не может выдавать binding v1.

Новые R5 backup manifests содержат `maintenance_fence_history`: commitment к полному event prefix, снятому при замороженном barrier и привязанному к deployment, archive barrier/fence, количеству событий и SHA256. Archive validation проверяет форму commitment; stopped-runtime verifier сравнивает сохранённый prefix с закреплённым старым maintenance DB, затем валидирует полную последовательность `begin/freeze/release`, event IDs/fences, финальные `maintenance_state.mode/barrier_id/fence`, три точных event triggers, остановленный runtime и неизменность закреплённых файлов. `maintenance_fence_lineage` возвращает archive barrier, текущий observed high-water, archived/current event counts и hashes внутри общего `evidence_sha256`; source-epoch preparation связывает этот hash со своим offline baseline. `MaintenanceFenceLineageV1` и `SourceGenerationV2` связывают это наблюдение с source generation как чистые DTO; они не читают хранилища и не выдают permission. Позднейший fence старого deployment наблюдается; отсутствующая, изменённая, неполная или противоречивая история блокируется.

Это локальное diagnostic evidence, не криптографически аутентифицированный ledger и не authority. Rewrite старым пользователем одновременно архива/restore metadata и maintenance DB, Windows ACL и host-level custody не квалифицированы. Старые manifests без optional commitment остаются пригодны для guarded data restore, но не проходят R5 lineage observation. Новый maintenance repository не создаётся и не получает high-water; отсутствие подтверждённой lineage оставляет successor blocked. Не принимать fence от caller и не выводить его из пустого control DB; guards и activation/outbound остаются без изменений.

**Synthetic acceptance до подключения consumers (ещё не закрыта):** process-bound tests на missing/v0 ticket в restored source; stale decision/generation; заменённый source path/file identity; один несовпавший authority; чужой participant/run/action/operation; replay одного ticket; barrier-first и ticket-first interleavings; crash после каждой source grant и перед final decision; отсутствующий/пониженный fence high-water; новый control DB без fixed ledger. Каждый runtime test должен требовать zero SQL/provider/native effects, все исторические guards сохранены и `activation_supported=false`. Текущие pure DTO tests покрывают только missing/unbound record, stale V1/V2 generation, checksum и scope rejection; они не закрывают межпроцессный ticket store/interlock. Отдельный grant-path тест запрещён, пока отсутствуют реальные актуальные owner/provider/native proofs; synthetic fixture не может вернуть `activation_granted`.

### R2: что обязательно удерживать

Весь backlog и его производные IDs: Secretary обычные prepare/STT/summary/identify jobs, authorized pipeline handoffs, enrollment operations и publication previews/outbox; Team commands/messages/resources; MAX inbox/replies/buttons/proposals/contexts; voice jobs/requests/proposals/notices; reminders/planner generations; sessions/codes/invitations/due/publication confirmations. Состояние `queued`, отсутствие receipt, expiry lease или новый UUID не доказывают отсутствие прежнего внешнего эффекта.

Старые `reserved/submitted/uncertain` Billing операции и accepted checkpoints сохраняются. Исторические completed/applied/sent/confirmed receipts не переписываются. Все старые исполнимые намерения получают durable no-replay disposition; неизвестные provider outcomes остаются неизвестными. Создание нового бизнес-действия после сверки требует нового явного подтверждения, а не автоматического повторения старого.

Quarantine связывает canonical source key, старое содержимое/состояние и parent lineage, включая completed rows: чтение старой квитанции допускается, порождение нового действия из старого button/context/proposal/handoff — нет. Новый derived UUID или attempt не отменяет принадлежность legacy lineage. Secretary job не всегда содержит точный per-call Billing operation ID; сопоставление по сумме/времени не принимается. Все старые Billing операции учитываются независимо и сохраняются, а source job/pipeline fence проверяется до порождения любого нового paid attempt.

Реализованный R2 preparer выдаёт только декларативный SQL-пакет запрещающих immutable dispositions. Исполнение — отдельная R3 controlled transaction с fresh operator approval; R2 standalone writer/apply отсутствует. Четыре protocol-v1 таблицы проверяются вместе с guard и исходными business schema/logical hashes; текущий file hash после записи должен фиксировать R3 отдельно. Типизированный Plan/Receipt или `existing=receipt` не заменяет фактический collector/durable readback/complete decision. Не снимается current guard и не открывается admission. Существующие receipts/dedup/replay histories остаются неизменными; смена state на fake `applied/sent` не заменяет disposition.

### R3–R5: разрешение только нового подтверждённого work

R3 реализован для inactive private copies: независимая current-Windows local operator policy/DPAPI/fresh typed consent, существующий closed original registry и exact stopped lifetimes, actual collector, writer locks/native OS lease, три durable readbacks и last complete decision. Operator policy не выводится из старой business-owner row. Retained metadata/archive/assets держат OS write/delete-denial leases до decision; WAL не удаляется/не конвертируется. Missing control не принимает prepared DB. Complete всегда остаётся blocked; реальная provider reconciliation не заявлена. Полный контракт, ограничения и подготовленные команды — [TEAM_R3_VALIDATION.md](../TEAM_R3_VALIDATION.md).

Участники: текущий доверенный локальный оператор/владелец, backup/restore authority, owned Supervisor/runtime, четыре связанные sources и реальные provider observations. Старая owner row в архиве сама по себе не подтверждает текущую роль. DPAPI доступ определяется выбранной Windows account, а не хешем ciphertext.

Fresh owner approval связывает restore UUID, manifest/metadata/bindings, полный inventory digest, source versions/watermarks, текущий scope и evidence. Под maintenance barrier проверяются exact owned old lifetimes и отсутствие неизвестных writers. Нет PID-only, lease-expiry или Boolean proof.

SQL файлы не имеют общего atomic commit. Сначала immutable preparations в authorities, затем финальный complete decision. Любая missing/changed/partial receipt удерживает весь deployment. Каждый разрешающий boundary проверяет тот же полный набор и конкретные source identities. Исторические guard rows не удаляются и не переводятся в ноль; будущий generation учитывает их как provenance и требует нового hold. На текущих схемах этот переход ещё невозможен.

### MAX после потери части inbox

После backup часть уже обработанных MID могла отсутствовать в копии. Quarantine только известных IDs этого не покрывает. `update.timestamp` не доказывает новизну. Официальный [Message](https://dev.max.ru/docs-api/objects/Message) и [GET /messages/{messageId}](https://dev.max.ru/docs-api/methods/GET/messages/-messageId-) документируют `timestamp` как время создания сообщения. Проверенные docs не дают явной гарантии replay immutability; GET 404 также допускает отсутствие доступа бота. Нельзя выводить из него «не отправлено».

[GET /updates marker](https://dev.max.ru/docs-api/methods/GET/updates) — курсор чтения; не заявлен атомарным cutover к webhook и не доказывает отсутствие уже доставляемых retries. Поэтому raw MAX text/media intake остаётся отдельной выключенной capability до реализованного cutover протокола и настоящих проверок. Canonical creation time может стать входом этого протокола; его нельзя назвать exactly-once или завершённой очисткой очереди.

Журнал `runtime_health_attempts` прежних subscription operations находится в control DB, которая не входит в четыре backup authorities. Quarantine этих четырёх источников не доказывает отсутствие прежней subscription попытки. Автоматическое восстановление подписки после restore также остаётся отдельной выключенной capability до протокола сверки actual subscription и current ownership. Новый пустой control DB не является такой сверкой. Старый bot event не может выпускать новый desktop login code: source-event lineage и restore issuance gate проверяются до выпуска.

## Stop / rollback

Остановиться на несовпадении hash/guard/path/schema, active journal, changed input, неполном inventory, неизвестном native lifetime, отсутствующем owner/provider proof или неподдерживаемой liability. Сохранить исходники и данные; не удалить journals/guards/uncertain, не повторять платный POST, не восстановить старый архив поверх рабочей системы. Возврат binary/config допускается только в отдельной папке с совместимой схемой и сохранением receipts.

Состояния доказательств раздельные: safe offline copy/preview; activation implementation; actual owner/provider reconciliation; manual phone/audio quality; operational restore/24-hour observation. Ни одно не заменяет другое. Внешний HTTPS ещё неизвестен и должен быть проверен по owner runbook до MAX/pilot.

### Дополнение 2026-10-12: versioned maintenance-ticket registry V2

Точный lifecycle registry V1 (`PRAGMA user_version` 0 или 1) сохраняет старые таблицы и остаётся доступен stopped-runtime verifier только для чтения. `MaintenanceRepository` при инициализации проверяет фиксированный набор таблиц/колонок и атомарно переводит V1 в V2; неподдерживаемая версия, лишняя таблица, неверная схема или отсутствующая часть V2 отвергаются до изменения registry. V2 (`user_version=2`) добавляет только `maintenance_ticket_commitments(ticket_id, record, record_sha256, created_at)`; lifecycle `maintenance_tickets` не меняется.

Записи commitments неизменяемы через update/delete/replace triggers и привязаны к существующему lifecycle ticket. Текущего producer/binder для runtime ticket нет; consumer wiring и новое permission не добавлены. Registry V2 — только persistence foundation, не авторизация; activation/outbound остаются OFF.
