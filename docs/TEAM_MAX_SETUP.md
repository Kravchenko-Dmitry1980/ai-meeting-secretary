## Профиль, бот и токен

1. Владелец самостоятельно входит в [MAX для партнёров](https://business.max.ru/) под своим доступным рабочим номером. Создаёт или выбирает профиль своего ИП и проходит верификацию по предложенному MAX способу. Официальная инструкция для ИП включает Госуслуги либо доступный банковский ID; имеющееся ИП само по себе не подтверждает профиль платформы. Коды входа и документы не передаются в Secretary/чат. [Подключение профиля](https://dev.max.ru/docs/maxbusiness/connection).
2. В разделе «Чат-боты» создаёт одного бота для поручений команды и заполняет карточку, соответствующую своему бизнесу. Название, описание и логотип готовятся до отправки; nickname выдаёт платформа. Проверка нового бота обязательна; официально указано до 48 часов по рабочим дням, это не гарантия фактического срока. Продолжать, когда модерация успешно пройдена и настройки доступны. [Создание и модерация](https://dev.max.ru/docs/chatbots/bots-create/create).
3. После успешной проверки открывает `⋮ → Настройки` своего бота и копирует токен локально. Там же находится настройка URL mini-app. Токен даёт управление ботом; при подозрении на раскрытие обновляется владельцем на платформе с последующим обновлением локального runtime. Не удалять бота ради обычной настройки. [Управление и токен](https://dev.max.ru/docs/chatbots/bots-create/manage).

Проектное решение: начать с личных диалогов трёх участников; добавление в группы не включать без необходимости и проверки сценария. Обработчик не использует групповой chat ID или отображаемое имя как право менять задачу. Владелец явно связывает каждого участника с точным MAX ID, реальным Vikunja user ID и project scope; первоначальная роль троих — `owner`, будущие участники получают минимальную необходимую роль.

Использовать локальную процедуру T12 с защищённым вводом и доступом только учётной записи runtime. Не считать placeholder или наличие переменной доказательством подключения.

## HTTPS и mini-app

Публичная форма пакета: `https://<домен>/team/` и same-origin `https://<домен>/api/team/v1/...`; webhook — `https://<домен>/hooks/max`. Proxy направляет только разрешённые API/webhook paths на `127.0.0.1:8766`, а public assets берёт из отдельного подготовленного release. Не размещать весь `frontend/dist`, корень проекта или `data` на веб-сервере.

После подтверждённого внешнего HTTPS владелец указывает URL `/team/` в настройках mini-app своего опубликованного бота. MAX допускает веб-файлы на выбранном hosting и требует HTTPS; mini-app привязано к боту. Наше размещение на собственном Windows-хосте — проектный выбор, а не требование купить MAX/cloud hosting. [Подключение mini-app](https://dev.max.ru/docs/webapps/introduction).

Официальный Bridge подключается с `https://st.max.ru/js/max-web-app.js`, даёт `window.WebApp` и строку `initData`; `initDataUnsafe` не является источником доверенной identity. Документация не требует отдельной инициализации объекта. Не добавлять недокументированный `ready()` как условие входа. [MAX Bridge](https://dev.max.ru/docs/webapps/bridge).

Подключение Bridge и runtime wiring относятся к T12. Отдельный static package T11 сам по себе не подтверждает загрузку SDK или возможность войти из MAX; существующий auth adapter ожидает данные Bridge при таком подключении.

В Secretary клиент отправляет только внутреннюю строку `window.WebApp.initData` в `/api/team/v1/session/max`; bot token остаётся на сервере. Gateway проверяет HMAC, уникальность полей, timestamp, replay и действующее членство. Это следует официальной подписи `WebAppData`; клиентская HMAC-проверка с bot token запрещена архитектурой проекта. [Валидация MAX](https://dev.max.ru/docs/webapps/validation).

Проектная policy строже рекомендуемого MAX окна: текущий `team_auth.py` принимает launch data не старше **300 секунд**, future skew не более **30 секунд**. Если открытое приложение не прошло bootstrap, закрыть и заново открыть mini-app; не сохранять старую launch string для повторного входа. Desktop вне MAX использует личный одноразовый код из бота, срок пять минут.

Публичный package должен разрешать точный официальный Bridge CDN в `script-src` только на Team HTML; не ослаблять CSP для local Secretary/API. Официальные страницы, проверенные здесь, не закрепляют полный список iframe ancestors или обязательный CSP. Поэтому web/desktop embedding и реальный native WebView требуют отдельного наблюдения и приёмки; не объявлять `frame-ancestors *` необходимым. Прямое чтение JS CDN инструментом завершилось internal error: байты, immutable version и SRI hash в этой карточке **не подтверждены**.

## Webhook и delivery

Официальный endpoint требует HTTPS:443, подходящее имя сертификата и полную доверенную цепочку. ACK — HTTP 200 не позже 30 секунд; после длительного отсутствия ACK подписка может автоматически исчезнуть. Параметр `secret` передаётся как `X-Max-Bot-Api-Secret`. [POST subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Проектный desired subscription: только свой `/hooks/max`, `update_types = [message_created, message_callback, bot_started]`, отдельный локальный secret. Текущий outbound host — `https://platform-api2.max.ru`; token передаётся в Authorization header, не URL. Серверный `MaxClient.register_own_subscription` проверяет свой маршрут до/после одного POST и не удаляет чужие подписки. GET показывает URL/types, но не доказывает верный secret или реальный callback. [GET subscriptions](https://dev.max.ru/docs-api/methods/GET/subscriptions).

Регистрация — внешнее изменение и выполняется только после готового проверенного local package и отдельного подключения владельцем. В T11 нет готового owner registration CLI: Python port не следует выдавать за команду, которую можно запустить с токеном в argv. Использовать только защищённую процедуру runtime T12, затем отправить настоящее тестовое сообщение с телефона и сопоставить durable event/ответ без сохранения чувствительного payload в отчёте.

Production работает через Webhook. Long Polling маркируется **DEV_ONLY**, одновременно с Webhook не включается и не квалифицирует круглосуточную доставку. Это ограничение самой платформы, а не обещание заменить ingress polling-ом. [Официальные события MAX](https://dev.max.ru/help/events).

## Бюджет и ручная приёмка

Локально настроить общий месячный approved предел **до 3 000 ₽**; меньший подтверждённый provider/key cap дополнительно ограничивает effective budget. В него входят встречи, voice STT, intent, единственный разрешённый repair и benchmarks. Отдельную скрытую квоту для голоса или старый произвольный лимит на встречу не вводить. Предупреждения 50/80/90% используют confirmed + reserved. AI останавливается при исчерпании; задачи, кнопки, запись и напоминания продолжают работать. См. [TEAM_REMINDERS.md](TEAM_REMINDERS.md) и договорённости T2.

Наличие токена Polza или trial не доказывает бесплатный STT. Перед первой платной пробой нужны явный бюджет и актуальное подтверждение выбранного тарифа; receipt фактической цены сохраняется в общем журнале. В документации T11 реальные облачные вызовы не выполняются.

На этапе T13 каждый из троих проверяет на своём настоящем телефоне: личный вход/отказ чужому пользователю; text и callback preview→confirm; native voice и отдельно audio file; board/matrix; изменение срока с причиной; quiet→09 напоминание и актуальную сводку; budget pause без остановки бесплатных кнопок. Отдельно пройти reboot/reconnect и восстановление без повторного применения команд. Приём MAX API не означает человеческое прочтение. Browser narrow viewport и mocks не заменяют телефон/MAX WebView; общий статус остаётся **NOT_QUALIFIED** до этих gate.
