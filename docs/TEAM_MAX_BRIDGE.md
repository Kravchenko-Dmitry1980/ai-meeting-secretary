# MAX Bridge и подтверждение внешнего срока: T12 frontend

## Вход

Team HTML загружает один официальный async SDK `https://st.max.ru/js/max-web-app.js`. Перед React/auth bootstrap приложение ждёт не более пяти секунд: уже существующий `window.WebApp`, событие загрузки, ошибку либо таймаут. После ошибки/таймаута используется явный `max: null`: поздняя загрузка SDK не запускает скрытую попытку MAX-входа. Одноразовый код на компьютере остаётся доступен.

Захватывается выбранный объект Bridge, а не ссылка на меняющийся `window.WebApp`. `initData` читается только auth-модулем и передаётся без переинтерпретации на сервер для проверки. Данные из URL, `initDataUnsafe`, browser storage и SDK-хранилищ для входа не читаются. Поле `WebApp.version` не используется как версия SDK или доказательство подлинности.

Событие `pagehide` отменяет ожидание SDK и немедленно закрывает auth lifecycle. Отменённый запуск не монтирует React; задержанный `/me:401` не начинает новый MAX credential POST после отмены. Уже отправленный запрос нельзя считать отменённой операцией только по закрытию страницы. React StrictMode сохраняет один bootstrap контроллера.

При восстановлении отменённой страницы из browser BFCache `pageshow.persisted` запрашивает свежую загрузку документа: старый закрытый lifecycle не используется повторно. Квитанция подтверждения проверяет operation UUID и task ID также в execution state, даже если `current` отсутствует.

[Официальная документация MAX](https://dev.max.ru/docs/webapps/bridge) описывает автоматическое создание `window.WebApp`; отдельный `ready()` не вызывается. На проверенной странице нет версии/SRI-хеша SDK. Пакет честно записывает unversioned CDN policy; реальные загрузка SDK, MAX WebView и телефонный вход ещё требуют T13 приёмки. Offline fake-DOM/auth тесты их не заменяют.

## Внешнее изменение срока

При `remote_due_unconfirmed` владелец открывает карточку задачи и нажимает «Проверить внешний срок этой задачи». Backend возвращает отдельное наблюдение: ранее подтверждённый срок, обнаруженный срок, baseline revision/fingerprint и observed fingerprint. Для других задач проекта проверка может не найти требующее решения наблюдение; это не означает отмену срока.

Владелец самостоятельно указывает точные дату и время по Москве или выбирает «Без срока», затем пишет причину. Поля не заполняются внешней датой автоматически. «Показать решение для подтверждения» создаёт серверный immutable preview; «Подтвердить решение» отправляет только его ID и стабильный operation UUID. Обычная команда `set_due` не обходит этот механизм, а raw `resolve_due` через generic commands не отправляется клиентом.

UI показывает принятие отдельно от исполнения. При неизвестном результате подтверждение не повторяется; «Проверить результат» выполняет GET по сохранённому operation UUID. До окончания ожидающей/неопределённой операции новое решение по той же задаче блокируется. Закрытие сверки или карточки не отменяет уже отправленную операцию; её состояние сохраняется в текущем сеансе/проекте и видно при следующем открытии карточки. При смене проекта, участника или session epoch старые данные скрываются и поздние ответы не возвращаются в UI.

Если версия/права изменились или preview истёк, нужно обновить задачи и получить новое наблюдение. «Обновить задачи» выполняет обычное чтение; frontend не меняет карточку оптимистически. Решение считается применённым только по backend receipt `applied` после проверки Vikunja.
