# Обработка и прогресс: проверка 2 октября 2026

## Подтверждённые причины

1. UI выбирал последний созданный job этапа. При 35 аудиофрагментах последний job оставался queued, скрывая running первого. Публичный контракт не отдавал version/chunk_id, необходимые для достоверного подсчёта.
2. Polza возвращает HTTP 400 / BAD_REQUEST именно из-за provider.max_price. Исходная ошибка была потеряна адаптером: сохранялся лишь HTTP-код. Повтор одного существующего фрагмента через worker и его журнал расходов подтвердил причину.
3. Отказ воспроизведён при STT ceiling 0.048, 0.05 и, после явного согласования владельцем, 0.10 RUB/min. Публичный и авторизованный GET модели сообщают 0.048 RUB/min для groq/deepinfra/deepinfra/us. Это расхождение каталога и действующего ценового фильтра; точная внутренняя ставка или дефект фильтра не установлены.

Полные записи запросов, аудио и ключ в этот документ не включены. Плата за эти отклонённые проверки не подтверждена: локальные резервы released; успешных квитанций нет. GET истории audio/failed за 2 октября вернул пустой список.

## Изменения

- Публичные jobs/SSE теперь включают version/chunk_id.
- UI агрегирует актуальные попытки текущей версии: running имеет приоритет, успешные уникальные чанки дают счётчик и progress. Нет выдуманных процентов или ETA.
- Отдельные состояния очереди, настройки, ошибки и лимитов; spinner только во время выполнения. Кнопки повторного запуска блокируются при активной работе.
- Отмена охватывает актуальные задания этапа, сначала ожидающие, затем работающие; существующие ограничения неизвестного оплаченного исхода сохраняются.
- Повтор при смешанных paused_budget/failed восстанавливает незавершённые чанки; исторические ошибки не создают новую оплачиваемую версию готовой расшифровки.
- Ошибка price_limit содержит фиксированное безопасное объяснение; UUID trace_id и допустимые code/param сохраняются, произвольное upstream body не попадает в UI/БД. Технические сведения раскрываются отдельно.
- Первый price_limit приостанавливает оставшуюся очередь данного этапа/версии/встречи.
- Ошибка polling уже принятой async-задачи не освобождает резерв; неопределённый расход остаётся unknown.
- Настройки обозначают тарифы как максимальные; публичная оценка каталога отделена от фактически подтверждённого расхода.

## Дополнительные исправления при полной обработке длинной записи

Все 35 аудиофрагментов прошли STT. При создании итогов выявлены ещё два дефекта:

1. Ответ на большой блок обрезался при 4 096 токенах. Это подтверждено read-only историей Polza: `finishReason=length`, `completion_tokens=4096`, а не предположением по общему сообщению. Настройки блока/ответа изменены на 12 000 UTF-8 байт и 8 192 токена; код отдельно сообщает `summary_output_limit`. Оплаченный отклонённый ответ остаётся в учёте.
2. Модель добавляла пунктуацию в цитаты из STT, и буквальное сравнение отклоняло весь протокол. Теперь совпадающая непрерывная последовательность слов восстанавливается в точный фрагмент источника, после чего проходит строгую проверку. Не допускаются пропуск/замена/перестановка слов, изменение отрицаний, имён и чисел; знаки чисел, дроби, даты, время, проценты и границы слов покрыты регрессиями. Сегменты не склеиваются для подбора цитаты. Это проверка происхождения текста, не доказательство смысловой правильности всех выводов.

Кроме того, ограниченный повтор HTTP 429 распространён на итоги. Уже подтверждённые шаги берутся из checkpoint; неопределённый POST и HTTP 5xx не запускают автоматический оплачиваемый повтор. Явное возобновление остановленных итогов открывает серию максимум из трёх попыток, не сбрасывая общий счётчик и оплаченные checkpoints.

После этих изменений пройден полный Python suite: **186 passed**, один upstream warning (`.venv\Scripts\python.exe -m pytest -q --basetemp .runtime\ptfinal3`). В диагностике сохранялись только коды, счётчики и признаки совпадений, без ключа или текста встречи.

Для готового JSON, не прошедшего проверку источников, добавлен один корректирующий LLM-запрос с исходными фрагментами и явным требованием удалить неподтверждаемые элементы. Новый ответ проходит ту же проверку; максимум два POST на такой логический блок. Все расходы учитываются отдельно, окончательный валидный результат кэшируется под исходным ключом. Ошибка транспорта или неопределённый исход не запускают коррекцию. Проверки после интеграции: **195 passed**, один upstream warning (`.runtime/ptfinal5`); прежнее ожидание одного POST в тесте ошибки доказательств обновлено на один исходный + один корректирующий запрос, с проверкой обоих расходов и отсутствия третьей отправки.

Qwen на этой записи всё равно не прошла проверку одного блока даже после коррекции; три валидных Qwen-блока сохранены, полный результат этой модели не объявлен готовым. Для обоснованной повторной обработки **только итогов** выбрана `openai/gpt-4.1-mini`. Авторизованный и публичный GET модели вернули HTTP 200; опубликованы `structured_outputs`, `response_format`, тарифы 46.7432/186.9728 RUB за миллион входных/выходных токенов на маршрутах Azure/OpenAI. Эти значения используются только как оценки при выключенных лимитах. Проверка модели и тарифов: [Polza](https://polza.ai/api/v1/models/openai/gpt-4.1-mini). Изменение модели создаёт другие ключи текстовых checkpoints; прежние результаты/расходы сохраняются, STT не повторяется.

## Частичный результат с явной проверкой качества

Если после одного корректирующего ответа отдельные решения, задачи или вопросы всё ещё не проходят строгую проверку источника, такие пункты исключаются из результата. Остальные пункты проходят прежний валидатор. Ошибки JSON/schema, транспорта и квитанций не маскируются этим поведением. Поле `excluded_items_count` сохраняется в checkpoints и итогах, суммируется по шагам и показывается предупреждением в UI и экспорте. Это число исключений из черновиков, не число уникальных потерянных задач; смысловую полноту и правильность должен проверить пользователь по расшифровке.

Полный Python suite после добавления этого контракта: **199 passed**, один upstream Starlette/httpx deprecation warning (`.venv\Scripts\python.exe -m pytest -q --basetemp .runtime\pf6`). Frontend typecheck, lint и production build прошли. Проверка helper прогресса ранее дала 21 passed; после неё helper не изменялся.

Один GPT-запрос завершился у провайдера, но ответ не дошёл до приложения. Автоматического повтора не было. По read-only истории подтверждены `finishReason=stop` и 0.49945109 RUB для `gen_2217244586978185217`; квитанция сверена и сохранена локально. Endpoint журнала ответа вернул 404, поэтому восстановить сам результат из Polza не удалось. После явного восстановления известного оплаченного состояния выполнено продолжение; эта стоимость остаётся в учёте. Диагностический файл `.runtime/repair-20261002/reconciled-gpt-receipt.json` содержит только метаданные квитанции.

На длинной записи найден также дефект объединения: порог для исходных текстовых блоков 12 000 UTF-8 байт применялся к уже сформированным протоколам, и очередной уровень не мог собрать ни одной пары. Исправление сначала использует прежнюю группировку. Если она не сокращает число частей или одна часть превышает размер map-блока, данные переупаковываются в пределах 40 000 UTF-8 байт. После интеграции полный backend suite: **203 passed**, один upstream warning (`.venv\Scripts\python.exe -m pytest -q --basetemp .runtime\pf7`). Независимая проверка изменения не выявила блокеров. Для загрузки исправления сервер штатно перезапущен после проверки отсутствия записи и активных заданий.
