# Обработка без лишних настроек — 16.10.2026

Принцип продукта: **«Меньше движений — больше пользы»**.

## Причина отказа

Приложение было запущено с `-Offline` для проверки сохранённого результата.
Этот режим намеренно запрещает облачные запросы, даже при сохранённом ключе.
Интерфейс отправлял пользователя в настройки без объяснения ограничения запуска.
Кроме того, форма удаляла из PATCH только `key_configured`, оставляя read-only
`max_upload_bytes`. Сервер отклонял запрос с технической английской ошибкой 422.
Существующий ключ Polza был настроен; повторный ввод не требовался.

## Изменённое поведение

- Сохранённый ключ используется автоматически. Настройки показывают «Polza подключена»
  и один переключатель обработки; инструкция подключения видна только без ключа.
- Модели, цены, размеры фрагментов и остальные параметры доступны в закрытом разделе
  «Дополнительные настройки». Их заполнение не требуется при обычной работе.
- Основная кнопка находится в карточке прогресса. При выключенном переключателе
  «Включить и обработать» включает его и продолжает выбранную запись за одно действие.
  Если ключ уже подключён, прежняя пауза больше не подписывается как необходимость
  настройки: показываются «Запись готова к обработке» и «Ожидает запуска».
- Продолжение сохраняет текущую версию аудио. После готового STT кнопка запускает
  только остановленные итоги. Новый платный анализ находится в отдельном закрытом
  разделе «Повторная обработка» и требует явного действия.
- Перед отправкой проверяются текущая встреча, версия, задания и состояние узнавания.
  Неопределённый исход оплаченного запроса не повторяется автоматически.
- В PATCH попадают только изменяемые поля; секреты и служебные сведения исключаются.
  Новый read-only `runtime_outbound_enabled` отличает Offline от пользовательского
  переключателя. Запрет Offline остаётся обязательным для API и провайдера.

санитизированном журнале не сохранялся. Ошибка не связана с отсутствием ключа,
PATCH 422 или тарифным потолком. Готового полного протокола и списка задач нет.

Повторной STT, автоматического повторного POST и изменения `uncertain` на успех
не было. Подтверждённые расходы итогов и неизвестные расходы STT/последнего запроса
учитываются раздельно; оценки двух ledger не складываются и не выдаются за оплату.

содержат ответа, `/log` вернул 404. Нулевая цена pending не доказывает отсутствие

содержание ответов по умолчанию не хранится; включать логирование без решения
владельца не стали. Расшифровка полностью доступна для ручной проверки сейчас.

В настоящем интерфейсе повторена операция «Сохранить настройки»: показано
«Настройки сохранены», ошибки 422 нет. Ключ не вводился заново.

## Последующее исправление timeout

Новый default ожидания ответа — 600 секунд; подключение по-прежнему ограничено
15 секундами. Сохранённый runtime параметр отдельно изменён через штатный PATCH
180 → 600 и прочитан обратно; default сам не перезаписывает старые настройки.
POST остаётся `request_uncertain`, без автоматического повтора. Для ConnectTimeout
сообщается лимит соединения; остальные timeout не выдаются за доказанную длительность
сессии. Необработанные сообщения исключений в ответ не включаются.

Затронутые provider/budget/context проверки: **241 PASS**, exit 0, 18,33 с;
JUnit `.runtime/team-rollout/offline-c45bf1fcb87847ae8d1511063b1ed658/junit.xml`.
Это последующий scoped прогон, его не складывать с предыдущими 35 проверками.
Pure проверка реальных ключей показала: 14 map requests идентичны при timeout
180 и 600, семь сохранённых checkpoints совпадают; timeout не входит в frozen
контекст и не требует повторной оплаты уже законченных шагов. Это не доказательство
восстановления неизвестного POST или успешного повторного live-прогона.

Текущий обычный API намеренно не обходит `uncertain` даже с `retry=true`.
Для отдельного понятного owner-действия определён
[контракт продолжения только итогов](contracts/uncertain-summary-resume-v1.md).
Он реализован и проверен ниже. Никакая новая платная попытка по этому контракту

## Явное продолжение итогов

В карточке теперь одно подходящее действие — «Продолжить итоги». Короткое окно
объясняет: расшифровка и готовые шаги сохранены, потерянный запрос мог быть оплачен,
незавершённый шаг может оплачиваться повторно. Ввод ключа или настройка модели не
нужны. Обычная основная кнопка и перегенерация не обходят эту неопределённость.

Новый POST требует strict acknowledgement и UUID команды. Атомарная immutable
lineage допускает только одного child для source; повтор команды возвращает тот же
job. Frozen context и exact checkpoints сохраняются. Родитель остаётся `uncertain`,
его неизвестный расход не освобождается; дочернее задание становится текущим только
для processing state. Миграция 10 содержит DB guards против обычного INSERT/UPDATE
в обход неизвестного leaf. Ограничения STT и общего бюджета не ослаблены.

Проверки последней карточки:

- Frontend: **332/332 PASS**, в том числе 14 новых recovery-проверок; typecheck,
  lint и production build exit 0. Идемпотентный intent, double click, смена встречи,
  fresh context, потерянный ответ, видимая ошибка внутри окна и отсутствие STT покрыты.
- Backend: **35 новых recovery-проверок**, входящих в прогоны **166 PASS**, последующие
  **3 PASS** и **73 PASS** для API/schema/restore/timeout. Это пересекающиеся scoped
  наборы, их не складывать с предыдущими проверками. JUnit: `offline-ae1ea886f9cd4f1091c820cb53145286`,
  `offline-f441e37b44ef41eaa240f25b1c7b60e6`, `offline-800480f6bb0a49bcb3da00375ed1a4a5`
  в `.runtime/team-rollout`.
- Restore compatibility: **95 PASS**, затем **12 PASS** (11 пересекаются): реальные
  синтетические schema 9/10 и v9 archive/restore, exact table/PK allowlists,
  неизвестные/неполные схемы закрыты; Team остаётся на 9. Lineage и восстановленный
  queued child остаются `no_replay`; исходный расход не меняется. JUnit:
  `offline-38a1cbe76a6d46ef98efec687e5fd3bf`, `offline-62e2fb83b9fc4beba9bedcf6d4469233`.
  Новый hash каталога требует повторной проверки старого sealed R3, автоматического
  переподписания нет. R4/admission и production gates не расширялись.

## Последствия для эксплуатационного плана

Старые P5-L supervisor/XML и P6 observer проверены только для `local_offline`.
Их нельзя использовать как автозапуск и суточную квалификацию нынешней рабочей
облачной обработки: прежний XML снова выключил бы основную функцию.
Перед применением P5 нужен соответствующий рабочему cloud scope вариант и review;
для P6 — политика наблюдения с допустимым изменением расходов, а не условием
неизменности Offline ledger. Старые evidence сохраняются в своём точном scope.
