## Вывод

Реально связанный вертикальный сценарий импорта существует: React → FastAPI upload → PostgreSQL/Celery/Redis → FFmpeg → faster-whisper + pyannote → OpenAI summary/tasks → API → React. Это полезный донор дизайна и отдельных идей, но не подходящая основа целиком для Windows V1 с SQLite и Polza. Реального Windows audio capture в исходниках нет. Наиболее пригоден небольшой слой презентационных React-компонентов; инфраструктуру, worker и HTTP-клиент требуется заменить.

Область аудита: весь собственный Python-код `app/`, `tests/`, `alembic/`, React/TypeScript/CSS `frontend/src/`, конфигурация сборки, Docker, зависимости, README/runbook, архитектурные аудиты и планы. Сборки, модели, картинки, generated egg-info и lockfile-исходники зависимостей не рассматривались как собственный код. Lockfile прочитан для версий и лицензий.

## Перепроверка предварительных дефектов

1. **FACT: автоматический demo fallback сохраняется.** `useMeetingProcessor.ts:99-100` запускает demo при пустом API URL; `:151-153` запускает demo на network failure. `runDemoFlow` создаёт `demo-*`, искусственные стадии таймерами и `FALLBACK_RESULTS`. No-key в Secretary должен быть waiting_config, а сетевой отказ — ошибка.
2. **FACT: отсутствующие таймкоды заменяются нулями.** `meetingApi.ts:263-264` содержит `Number(record.start ?? 0) || 0` и аналогичный end. Legacy plain transcript получает `timestamp: String(index + 1)` (`:253`), хотя ordinal не время. Alignment `_sanitize_bounds` удлиняет некорректные границы на 0.05 sec. В новом контракте нужны nullable ms и timing_precision.
3. **FACT: confidence scale неверно показывается UI.** `task_extraction_service.py:47,94-96` использует 0..1; API `routes.py:303` отдаёт без преобразования; `MainPage.tsx:577` добавляет `%` напрямую. 0.88 отображается как 0.88%, а demo содержит 92/81. Новый UI должен либо преобразовывать в процент, либо не выдавать self-reported LLM confidence за измеренную достоверность.
4. **FACT: готовый пустой список задач трактуется как ошибка.** `routes.py:292-293` отдаёт 404 при `tasks=[]`; frontend `fetchMeetingResults` использует `Promise.all`, так что отказ tasks блокирует summary/transcript. `task_extraction_service.py` при невалидном ответе тоже возвращает [], смешивая error и empty. Требуется 200 [] для succeeded и отдельное состояние error/processing.
5. **FACT: browser key в localStorage.** `MainPage.tsx:79-82` сохраняет весь FrontendSettings в `meeting-secretary-settings`; `types/meeting.ts` включает apiKey; `useLocalStorage.ts:4-10` читает и сериализует значение. Это старый shared APP_API_KEY, а не Polza key, однако практика непригодна. В Secretary ключ Polza только backend/.env; CSRF токен memory-only.
6. **FACT + INTERPRETATION: частичная защита от дублей есть, гарантии нет.** `tasks.py:92-106` пропускает done/in_progress и `:286` заменяет задачи; summary переиспользуется `:258-268`. Однако SELECT then update не atomic claim, уникальных ограничений нет. После failed повтор начинается с нового Transcript (`:161-168`), удаляются segments только новой версии (`:211-217`), а `/segments` объединяет все transcripts (`routes.py:260-263`), в отличие от `/transcript`, выбирающего latest. Следовательно, повтор после late failure может выдавать двойной timeline. Удаление прежних speakers при наличии FK старых segments может дополнительно прервать retry на PostgreSQL. Crash оставляет in_progress, который ранний guard вечно пропускает. Это вывод по активному пути, не воспроизведённая конкурентная гонка.
7. **FACT: raw transcript фактически теряется.** В памяти V2 хранит raw/clean, но persisted `TranscriptSegment.text` получает clean (`tasks.py:234`), а `Transcript.full_text` перезаписывается `build_readable_transcript` (`:238-241`). Нет versioned linkage summary → transcript.
8. **FACT: частичный отказ diarization маскируется.** Worker пишет SPEAKER_01 fallback и stage diarized; API/UI не получают явный статус «диаризация отсутствует». Channel microphone/system также нигде не реализован.
9. **FACT: метрики не сохраняются в DB.** `tasks.py:317` проверяет `hasattr(job, 'metrics_json')`, но models/migrations такого поля не имеют; есть только logs. Текущие latency/quality numbers не доказаны этими исходниками.
