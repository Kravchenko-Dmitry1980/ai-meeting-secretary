# P6-PREP: подготовка доказуемого суточного наблюдения

Дата: 16.10.2026. **Реальный P6 не начат.** Подготовка исходников и синтетические
проверки не заменяют приёмку P1–P5 или разрешение владельца на запуск наблюдения.
Приложение продолжает работать в прежнем ручном Offline режиме; Scheduler не менялся.

## Выявленный пробел

Старый `.runtime/uptime-watch-20261010.ps1` наблюдал PID/creation time, `/health`,
CPU/RAM на жёстко заданном адресе. Он не фиксировал commit/scope, `/ready`, сохранность
принятых задач, расходы, резервную копию и покрытие ошибок. Исторический файл
`RUNNING` не доказывает наличие работающего monitor или завершение 24 часов.

Новый сбор должен привязываться к версии **запущенного** приложения. Чистый HEAD
в момент просмотра не доказывает, какой код загрузил ранее запущенный Python.
Поэтому supervisor фиксирует candidate binding при запуске; неизвестная/изменившаяся
привязка не допускается для квалификации. Обычный запуск приложения остаётся доступен.

## Наблюдаемые факты и ограничения

| Критерий | Источник | Что он доказывает |
|---|---|---|
| Health | `GET /health` | Ответ HTTP; сам по себе не подтверждает работу очереди |
| Worker | `/ready.components.processing_worker` | Возраст heartbeat и liveness; heartbeat обновляет отдельная coroutine, это не счётчик обработанной работы |
| Очереди | `/ready.jobs` и локальные записи jobs | Динамика относительно начального состояния; исторические ошибки не приравниваются к новым |
| Хранилище | `/ready.components.storage` и database | Свободное место, доступность, integrity; `os.access` не является реальной пробной записью |
| Версия/ownership | Candidate binding, реальные identities supervisor/launcher/listener | Связь конкретного чистого checkout и frontend с проверяемым запуском |
| Принятые задачи | Текущая проекция tasks/assignments + согласованные ID/версии | Сохранность и актуальная валидность назначения; старая confirmed snapshot сама по себе недостаточна |
| Расход | Локальный ledger через SQLite `mode=ro`, `query_only` | Изменения локальных квитанций и unknown; это не баланс Polza в кабинете |
| Ошибки | Ограниченное чтение error log и его непрерывность | Новые категории/количества/хеши; пропуск ротации не равен нулю ошибок |
| Backup | Согласованный manifest и verify | Проверяемая копия в конкретном составе; возраст показывается без самовольно назначенного RPO |

`GET /api/v1/cloud-budget` не использовать как строго read-only снимок:
его snapshot открывает `BEGIN IMMEDIATE`. `doctor.ps1` и
`POST /ready/storage-probe` выполняют запись. Observer не вызывает их и не
обновляет внешний баланс. Read-only SQLite не обещает отсутствие служебных WAL/SHM
sidecar-файлов; бизнес-данные через него не изменяются.

## Контракт подготовки

- Только `local_offline`, literal loopback, явные checkout/DATA_DIR и новый каталог
  evidence внутри `.runtime`. Без proxy, redirects, облака и автоматического restart.
- Принимаются реальные owner-approved задачи и evidence P1–P5. Пустой/неподтверждённый
  baseline не превращается в квалификацию. Синтетические тесты используют только
  явно тестовые inputs; фиктивное согласие владельца для рабочего запуска не создавать.
- Candidate: чистый Git SHA, канонический checkout и ограниченный digest frontend.
  Binding запуска, текущий checkout и ожидаемый кандидат должны совпадать.
  Переполненный/неизвестный набор файлов приводит к отказу, а не усечённому hash.
- Сохраняются ID, версии, числовые показатели, категории и хеши. Тексты поручений,
  расшифровки, имена, токены, сырые ошибки и HTTP тела в журнал не записываются.
- Нужны настоящие не менее 24 часов: UTC + монотонное время, контроль boot/identity,
  пропусков и изменения часов. Короткий тест с подменёнными часами проверяет
  алгоритм, но не закрывает P6.
- Изменение расхода Offline, потеря/дублирование/изменение принятых задач,
  неизвестная identity, смена SHA, потеря log coverage или недостаточные данные
  не могут закончиться PASS. Неизвестный расход сохраняет отдельный смысл.
- Все Team-метрики для этого scope — N/A. Наблюдение простоя Offline не доказывает
  качество новой расшифровки, платные запросы, настоящую доставку MAX или Team recovery.
- Даже успешный журнал наблюдения — только часть evidence P6. Решение о выпуске
  остаётся отдельной P7-приёмкой; `production_qualified` вручную не изменяется.

## Поставляемая подготовка

`scripts/local_observation.py` предоставляет команды `observe` и `evaluate`.
`scripts/local_candidate.py` связывает чистый checkout и frontend с запуском;
supervisor сохраняет результат в своей ownership receipt. Observer проверяет
настоящие PID/creation time/ancestry/listener, а не только существование JSON.

Сборщик использует реальные GET, read-only SQLite и файловые журналы. Журнал
`samples.jsonl` связан последовательными SHA-256 и hash конфигурации; имеются
отдельные terminal/report. Запись ограничена 1 МиБ на sample, 64 МиБ на весь журнал
и 200000 samples. Превышение останавливает сбор с явным незавершённым результатом.
Существующий output никогда не перезаписывается, возобновления старого журнала нет.
Чтение HTTP ограничено 1 МиБ, логов — 6 МиБ на файл. Границы чтения и потеря
непрерывности не превращаются в пустой успешный результат.

Обычно задаются interval 60 с и maximum gap 90 с. Первый и последний samples
полностью проверяют выбранную копию; промежуточные сверяют manifest/receipt.
Отсчёт 24 часов начинается после завершения начального sample. UTC, monotonic
и boot identity проверяются совместно. Финальный статус `OBSERVATION_PASS`
означает только непрерывность наблюдения в заданном scope; остальные статусы
`INCOMPLETE`, `INTERRUPTED`, `NEEDS_REVIEW` не допускают приёмку P6.

Нормальная успешная работа локальных очередей допускается. Новые либо повторные
ошибки требуют review. Неизменный исторический unknown-расход остаётся unknown,
а не нулём. Новые расходы в этом Offline scope требуют разбора.

### Входы для будущего рабочего запуска

1. Фактическая приёмка P1–P5 и минимум трёх задач владельцем. Сохранить локальную
   receipt с `schema_version: 1`, `scope: local_offline`,
   `accepted_gates: [P1, P2, P3, P4, P5]` и выбранными `accepted_tasks`.
   Файл только фиксирует состоявшееся решение человека; создавать его заранее нельзя.
2. Каждая задача задаётся `meeting_id`, `transcript_version`, `summary_version`,
   `assignment_revision`, `action_id`. Использовать реально подтверждённые назначения
   текущей версии. Не подставлять synthetic IDs или подтверждения тестового стенда.
3. Конфигурация schema v1: `scope`, `candidate`, literal `origin`, абсолютные
   `data_dir`/`runtime_root`, `interval_seconds`, `max_gap_seconds`, `accepted_tasks`,
   `owner_acceptance: {path, sha256}` и `backup`. Candidate содержит `state: bound`,
   `project`, `git_sha`, `frontend_sha256` и совпадает с запущенным supervisor.
4. Backup содержит `directory`, `manifest_sha256`, `verify_receipt`,
   `verify_receipt_sha256`, `excluded_directories`. Для текущей согласованной копии
   разрешён только массив `[test-audio-tmp]`; оригинал не изменять. Пути и хеши
   сверять с P4 evidence. Копия на том же диске не защищает от потери диска.
5. Явное решение владельца начать полные 24 часа. Конфигурацию сохранить локально
   в `.runtime`, выбрать новый output. Пример точной структуры есть в поставляемом
   native fixture, но его `synthetic: true` receipt не является рабочей приёмкой.

Команды **будущего рабочего запуска, сейчас не выполнены**:

```powershell
& .\.venv\Scripts\python.exe -B scripts/local_observation.py evaluate --output 'D:\AI\Projects\Active\Secretary\.runtime\p6-owner-observation'
```

Первая команда занимает реальные 24 часа. Запускать её в согласованной сессии;
планировщик/автоматизация этой подготовкой не устанавливаются. Ctrl+C сохраняет
незавершённый результат, не останавливая Secretary. Exit 0 возможен только для
`OBSERVATION_PASS`, exit 2 — незавершённые/непринятые результаты или ошибка входов.
При смене кода, процесса, версии принятых задач либо пропуске данных сохранить
журнал, разобрать причину и согласовать новый период; не редактировать старые samples.

### Проверки подготовки

Focused и отдельный короткий native fixture:

```powershell
& .\.venv\Scripts\python.exe -B scripts/run_offline_tests.py tests/test_local_observation.py tests/test_local_supervisor.py tests/test_offline_launcher.py tests/test_readiness.py -q
& .\.venv\Scripts\python.exe -B tests/local_observation_native_fixture.py --run
```

Native fixture разрешён только на чистом commit. Он создаёт собственные маленькие
синтетические данные, три подтверждённых тестовых назначения, cold backup и Offline
процесс на отдельном loopback port. Длительность наблюдения — пять секунд;
ожидаемый результат самого P6 строго `INCOMPLETE / full_day_not_observed`.
Fixture проверяет техническую связность, штатно останавливает только свои процессы
и сверяет сохранность основного runtime. Это не запуск рабочего P6.

Окончательные evidence и SHA короткой native проверки добавляются после review
и исполнения на чистом кандидате. Полный suite относится к финальному кандидату P6.
