1. `restore_fresh_evidence.py:prepared_restore_evidence(...)` получает сведения только из фактических существующих R3/V1/source-proposal authorities и четырёх подготовленных источников. На время наблюдений удерживаются Windows leases против записи/удаления; до выдачи и после выхода повторно проверяются источники, receipts, архив/assets и остановленный runtime. Caller не передаёт готовый proof, epoch или validator. После закрытия диагностический объект больше не работает.
2. `restore_provider_observation_store.py` хранит отдельную неизменяемую историю наблюдений и purpose approvals. Строгая схема, hash chain, FileID, отсутствие sidecars, TEMP/ATTACH и срок действия проверяются при чтении/append. Потерянный или повреждённый существующий журнал не пересоздаётся. Пределы: 512 records / 1 MiB суммарных payload / 64 KiB payload / 64 approvals / 8 MiB DB. Новая история не переписывает исходные R3/V1/source preparations.
3. `restore_provider_observations.py:observe_restore_providers(...)` — явный production GET-only issuer. Он сам получает retained source evidence, закрепляет явный private JSON текущей конфигурации и повторно аутентифицирует свежий Windows operator approval для `restore_provider_observation`. Публичный API не принимает client/transport/clock/proof/URL/epoch/capability. Точные credential/resource/config hashes и интервал одного GET сохраняются в журнале. Private synthetic seam помечает каждую запись `synthetic_get`.
4. `restore_business_owner.py:BusinessOwnerAuthority` создаёт отдельную текущую локальную owner policy под CurrentUser DPAPI/private ACL и выпускает свежий purpose receipt `restore_activation_consent`. Назначение business role требует явной новой human ceremony с проверкой UUID, MAX/Vikunja ID и project scope. Старая Team owner row, session, Windows operator policy или runtime setting не назначают business owner автоматически. MAC domain/key и anchor `.runtime/team-business-owner` независимы от operator.

Owner-policy — явно выбранный локальный trust root, такой же по характеру human identity mapping, как первый owner bootstrap. Она не доказывает удалённое владение аккаунтом MAX/Vikunja. Подписанный owner commitment связывает hashes, а не подтверждает семантику provider facts. Его nonce пока не потребляется финальным activation decision; production factory полного owner/provider grant и общий predicate остаются следующим обязательным шагом.

## Что именно читается у провайдеров

| GET | Подтверждаемый факт | Что нельзя выводить |
|---|---|---|
| Polza `/api/v1/key` | Текущие aggregate usage/limit/reset для точных использованных bytes ключа | Включение конкретной старой операции; нулевой неизвестный расход; разрешение release |
| Polza `/api/v1/history/generations/<saved-id>` | Exact saved request ID, terminal/pending status и provider RUB cost | `provider_job_id` вместо history ID; guessed period; автоматический settlement/replay |
| MAX `/me` | Точный configured bot ID и `is_bot=true` | Business-owner identity; доставка сообщения; cutover |
| MAX `/subscriptions` | Текущий список после matching `/me` в том же issuer/credential scope; URL сохраняется только как hash | Webhook secret possession, реальная доставка/retries, отсутствие прежнего POST |

Используются прямые owned HTTPX transport, TLS verification, `trust_env=false`, redirects/retries OFF. Polza account GET при смене периода получает unavailable вместо скрытого второго GET. JSON/body bounds, duplicate fields, encoding, exact IDs и типы проверяются. На GET batch действует 30-секундный deadline; source/archive/config inspections — отдельная файловая работа, их полный SLA не квалифицирован. При исчерпании deadline сохранённые records остаются, ответ явно `partial_observations_blocked`.

Наблюдения истекают максимум через 300 секунд после GET и не позднее operator approval. Changed config/credential/operator/source, обратное время и expired approval отклоняются до append. Нельзя освежить record простым чтением старого журнала.

Фактический Billing inventory `reserved/submitted/uncertain` ограничен 128 строками для этого observation protocol. Слишком большой inventory требует отдельной поддерживаемой карточки; его нельзя урезать. Отсутствующий request ID, другой старый key tag, pending/404/error остаются неопределёнными. Gross hold и исходные Billing строки сохраняются даже при terminal history fact: этот issuer не выполняет settlement. Лимит Polza **3000 ₽/месяц** не меняется, дополнительные тарифные потолки не вводятся.

Vikunja в этой карточке остаётся остановленной с prepared native hold; наблюдение возвращается как `unavailable_native_hold`. Обычный native startup для получения GET не обходит ещё не реализованный global pre-Popen predicate. Raw MAX intake и automatic subscription reconciliation также остаются отдельными выключенными capabilities.
