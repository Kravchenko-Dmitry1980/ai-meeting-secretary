# Общий бюджет Polza

Secretary и будущий Team Gateway используют один `data/billing.sqlite3`. Approved budget — 3 000 ₽ в месяц минус явно согласованные внешние расходы (по умолчанию 0). Меньший месячный лимит API-ключа Polza становится действующим пределом; приложение не меняет его в кабинете провайдера.

Платный POST требует актуального GET `/key`, месячного reset, проверенного лимита и атомарного резерва. Цена берётся из публичного каталога точной модели. Это оценка, а не гарантированная верхняя цена маршрута. Реальный месячный предел также должен быть установлен у Polza; отсутствие/иной период/превышение согласованного лимита приостанавливают новые запросы.

Production factory `build_polza_client` подключает guard для STT, каждого summary map/reduce/repair и последующих голосовых команд. Старые `provider.max_price` и ограничение встречи в этом пути не применяются. Legacy usage API сохранён для совместимости; сумму месяца определяет новый журнал. Прямой клиент без guard может работать только с явно переданным `httpx.MockTransport`; реальный платный запрос отклоняется.

Все деньги в журнале — целые micro-RUB. Один POST имеет один UUID операции; async polling использует ту же операцию. Timeout, повреждённые суммы/валюта и потеря квитанции сохраняют резерв. Уже наблюдённую сумму не уменьшает следующая повреждённая квитанция. Расход из неверного результата учитывается до проверки текста/ID. Автоматический повтор платного отказа с указанным или неоднозначным расходом запрещён.

Начало периода — 1-го числа в 01:00 Москвы. Неподтверждённые расходы сохраняются при смене месяца и ключа. Запоздавший автоматический GET не отменяет явную смену активного ключа владельцем.

## Owner-local API

Изменения требуют `X-Secretary-Token` из `/api/v1/session` и действующей localhost-проверки Host/Origin. Эти пути относятся только к локальному Secretary; публиковать их через будущий Team proxy нельзя.

- `GET /api/v1/cloud-budget` — снимок approved/effective/confirmed/reserved/remaining и причина паузы.
- `POST /api/v1/cloud-budget/refresh` — чтение лимита/расхода Polza; явное действие также разрешает смену активной идентичности ключа.
- `POST /api/v1/cloud-budget/scopes` с `operation_id` и `cap_rub` — сохраняемый лимит явно разрешённого benchmark внутри общего месячного бюджета. Replay с тем же UUID/суммой возвращает тот же scope; другая сумма даёт 409.
- `POST /api/v1/meetings` принимает необязательный `cloud_budget_scope_id`; worker автоматически учитывает расходы этой встречи в scope.
- `GET /api/v1/cloud-budget/scopes/{scope_id}` — стоимость и резервы прогона, `uncertain_count`; исчерпанный оплаченный scope отличается от неизвестного исхода.
- `POST /api/v1/cloud-budget/operations/{operation_id}/reconcile` — только бесплатное чтение истории по сохранённому точному provider ID и исходному ключу. Нет ID/подтверждённой суммы — резерв сохраняется; повтор оплаченного POST не выполняется.

## Ограничения доказательства

Опубликованный `/key` не имеет `as_of`, billing watermark или списка включённых generation IDs. История подтверждает отдельную сумму, но `createdAt/completedAt` не являются документированным временем списания. Поэтому рост агрегата не используется как доказательство включения определённой квитанции, а поздний расход не относится к месяцу по догадке.

Подтверждённые квитанции не дублируются. Неопределённое пересечение агрегата и локальных квитанций может дополнительно удерживаться в `reserved_rub`; это не объявляется подтверждённым списанием. Снятие такого резерва требует надёжного provider inclusion proof; текущий публичный контракт его не предоставляет. Реальный authenticated account/history и billing behaviour пока не квалифицированы, выполненные тесты используют синтетические ответы.

Benchmark меняет только собственный `cloud_enabled` при необходимости. При неизвестном исходе он сохраняет cloud pause; обычные цены/переключатели/лимиты встреч не переписывает. `--max-rub` задаёт scope этого прогона, а не общий лимит приложения.
